# Architecture

## Overview

AI Audit uses a single-cluster architecture with one main control-plane node and multiple Docker-capable compute workers. The main node owns product state and scheduling decisions. Compute workers own isolated execution of Codex runs.

## Components

### Frontend

The frontend is a web application with:

- Login and session management.
- Workspace list, upload, fork, and share workflows.
- Chat interface with real-time progress.
- Artifact browser and download controls.
- Admin views for users, groups, budgets, usage, and audit logs.

The chat UI should support websocket or SSE updates for model output, progress events, tool calls, errors, budget warnings, stop events, and completion events.

### Backend API

The browser-facing control plane is a FastAPI ASGI application served by a
single Uvicorn worker. It provides:

- Authentication and authorization.
- User, group, and budget management.
- Workspace metadata and permission checks.
- Chat session and run lifecycle APIs.
- Worker scheduling.
- Event persistence and real-time event fanout.
- Artifact discovery and download authorization.
- Audit logging.

The backend is the only component trusted to make access-control and budget decisions.

The current deployment keeps one API/scheduler process because login sessions
and scheduler ownership remain process-local. Chat sessions, runs, and events
use normalized row storage: SQLite is the zero-configuration development
backend and PostgreSQL is selected in production through
`AI_AUDIT_DATABASE_URL`. Uvicorn's asynchronous transport allows many idle SSE
connections without dedicating one operating-system thread to each connection.
Chat event reads and writes do not take the workspace lifecycle lock; lifecycle
coordination is scoped by workspace, group, session, or run, with only short
workspace metadata commits using the compatibility database lock.

### Metadata Database

The database stores product metadata, not large workspace file payloads:

- Users, groups, memberships, account state.
- User and group budgets.
- Workspace records, permissions, forks, lightweight checkpoints, and bounded file-version metadata.
- Chat sessions, runs, model settings, lifecycle state.
- Token usage records.
- Artifact records and checksums.
- Audit logs.

### Shared Filesystem

The shared filesystem is mounted by the main node and every compute worker. It stores:

- Uploaded workspace files.
- Managed workspace directories.
- Current workspace files and content-addressed current/previous file blobs.
- Generated artifact bundles.

Workspace paths must be generated by the backend and must not be directly derived from user-controlled names.

### Compute Workers

Each compute worker runs a lightweight worker agent. The worker agent:

- Answers health probes from the main node.
- Reports capacity, active runs, and health.
- Receives start and stop commands.
- Receives authenticated resumable upload chunks and finalizes workspace files on shared storage.
- Launches one Docker container per active Codex run.
- Mounts the assigned workspace path into the container.
- Applies CPU, memory, timeout, and network policies.
- Streams run events back to the backend.

## Scheduling

The scheduler runs on the main node. It assigns queued runs to healthy workers based on:

- CPU and memory capacity.
- Workspace lock availability.
- Account and group budget status.
- Worker heartbeat freshness.

Among compatible nodes, the scheduler chooses the assignment with the lowest maximum projected CPU/memory utilization and uses configuration order as the deterministic tie-breaker. If no worker has capacity, the run remains queued. If a worker becomes unhealthy, it stops receiving new runs. Active work is protected by a renewable lease: on control-plane loss the worker stops the container, and on worker loss the control plane waits out that lease before recording the run as failed/resumable. Runs are not automatically retried because workspace mutations may already have occurred.

Control-plane/worker traffic uses HTTPS with CA verification and a shared bearer secret supplied only through the environment. The worker protocol is limited to health, run start, status/event polling, stop, lease renewal, and terminal acknowledgement/cleanup. Worker identities and capacities are static configuration, not self-registration.

## Isolation

Each active run executes in a separate Docker container. The container receives:

- A mounted workspace directory.
- Session-specific environment configuration.
- Resource limits.
- A constrained user identity inside the container.
- Access only to approved tools and paths.

The system should assume uploaded files may be sensitive and untrusted. Containers should not receive direct database credentials or broad filesystem access.

## Core Entities

- `User`: an internal account.
- `Group`: a collection of users with shared access and optional shared budget.
- `Budget`: token allowance for a user or group.
- `Workspace`: a managed directory of audit files.
- `WorkspaceCheckpoint`: a lightweight lifecycle boundary; current file state is used for fork/resume and pre/post scans produce artifact comparisons.
- `ChatSession`: a user-facing conversation attached to a workspace.
- `Run`: one execution attempt inside a Codex container.
- `Artifact`: a generated or modified file available for download.
- `AuditLog`: security and operational event record.

## Operational Logs

The system should record audit logs for:

- Login success and failure.
- Workspace create, upload, share, fork, and delete events.
- Chat start, stop, resume, completion, and failure.
- Artifact download.
- Admin budget or account changes.
- Permission denials.
- Suspicious account usage signals such as concurrent session violations or unusual IP/device changes.
